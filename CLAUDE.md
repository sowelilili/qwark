# qwark

PS3 VSH plugin (SPRX) that owns the RaCMAN trainer logic for the four original Ratchet & Clank games, and, in test builds and the PC builds, Tools of Destruction (game 5, revision 1.27). Read `../docs/DESIGN.md` (architecture, section 3) and `docs/PROTOCOL.md` (the wire contract) before changing anything.

## Build

PS3 (`qwark.sprx`): run `_Make.bat` from Windows, or in a Cygwin login shell:

```
/c/cygwin64/bin/bash.exe --login -c "cd '/cygdrive/c/Users/atune/Documents/RaCMAN Development/rewrite/qwark' && make"
```

**Test builds and release builds** (revision 1.24, PROTOCOL.md 3.1.1). A plain `make` (and `_Make.bat`) builds a *test* module: it sets SessionInfo `flags2` bit4 DEV, and HELLO carries its build ID, the CRC of the sources (`tools/buildid.py`). `make` writes `qwark.build` (build, dev, id) beside `qwark.sprx`, and `make dist` copies it into `dist/`. The client replaces a DEV module whose ID is not its own module's, so every test build reaches the console without a new build number. A release is `make release` (`make QWARK_DEV=0`, then `make dist`), whose module has no DEV bit and is judged by its number alone; the client's `release.ps1` refuses a `dist/` whose `qwark.build` says `dev 1`. `build-host.sh` makes `qwark-host.exe` a test build with the same ID, and `qwark-rpcs3.exe` neither.

**Preview features** (PROTOCOL.md 3.1.2). `QWARK_PREVIEW` (src/core/proto.h) builds in the features still being tried out, build 56's settings profiles and USB mods; it follows `QWARK_DEV` unless given itself, so `make` has them and `make release` compiles them out (no `modusb.c`, no profile code, their ops UNSUPPORTED, their bits clear). Keep each such feature behind `#if QWARK_PREVIEW` with a stand-in for its callers that does what the last release did. `build-host.sh` and the unit tests build them in; `test/run.sh` also builds `test/test_release.c` with `QWARK_DEV=0 QWARK_PREVIEW=0` into `test/qwark-test-release.exe`, which checks they are gone.

**Game modules** (revision 1.26, PROTOCOL.md 9.11, `src/games/module.h`). `QWARK_GAME_MODULES` follows `QWARK_DEV` like `QWARK_PREVIEW`: a test build's core links no game, and `make` then builds `rac1.sprx` .. `rac4.sprx` (`make games`), each named for its game, never for its number (the title index's `title_module_name`, the makefile's `GAME_MODULES`, the installer's `INST_GAME_NAME_n`, and the client's `GameModule.FileName`; a later game is a name of its own, Tools of Destruction's `tod.sprx`), each one R-X segment and nothing writable, merged and checked by `tools/gamemodule.py` and signed like `qwark.sprx`; `make dist` copies them and the installer package carries them. `make release` links the games in as before (`QWARK_GAME_MODULES=0`) and deletes any module left over. Every game source starts with `#include "core_import.h"`, which renames the core functions a game calls (the list is `src/games/core_api.txt`; run `python -I tools/coreapi.py` after changing it and commit what it writes) to wrappers that go through `struct core_api`, in the host builds too; `test/run.sh` holds the game objects to that (`coreapi.py nmcheck`). A game's mutable statics live in one struct per file (`struct rac1_state`, `R1->...` behind the old names), which a module keeps in the core's lent state area and a linked build in a static; a module has no writable data at all, so a new static in a game file fails `make games`. Anything a game must do in a boot's first seconds belongs in the title index (`src/games/titles.c`), not the game: a module may arrive seconds into the session. Every network-thread use of `session_game()` takes the core lock and copies what it needs before letting go (the lock audit, PROTOCOL.md 9.11). **Tools of Destruction** (revision 1.27, `src/games/tod*.c`, `tod.h`) is game 5 and `tod.sprx`, only where `QWARK_HAS_TOD` (`src/core/buildmodes.h`): a test build, the host builds and the tests, never `make release`, which keeps the four and has no room for a fifth (titles.c lists no ToD there, and the Lua ops answer UNSUPPORTED). The makefile names each module's vtable (`GAME_VTABLE_<name>`). Its game's own Lua is the core's (`src/core/luacore.c`, LUA_EXEC/LUA_STATUS/LUA_PATCH, PROTOCOL.md 5.15) over the mailbox of `src/core/luamb.h`, with the helper's bytes in `tod.sprx` (and the emulator builds) through `game_api.lua_desc`; the helper itself is `src/games/luahelper/`, built by `make luahelper` (and `luahelper-if-stale` in `all`) into the committed `src/games/luahelper_bins.c`. Everything else ToD does is plain data reads and writes, so it all works under RPCS3, but for Fast loads (revision 1.29), a code patch of LoadScreen_Update on a console and a code switch under RPCS3 (`src/games/switches/sw_tod.s`, `tod.h` TOD_FASTLOAD_AT), with three pieces of qwark's own (`own_*`, in `switches_own.c` only where `QWARK_HAS_TOD`, a console writing them with the patch) for the departure and the story FMV loads; nothing polled goes through Lua. Its savefile manager is the game's own save system driven by data writes (`src/games/tod_save.c`, `game_api.savefile_driver`, docs/tod-savefile.md), so ToD has no savefile helper code and no RPCS3 patch. Its console menu (revision 1.29, docs/tod-menu.md, PROTOCOL.md 9.12) is the game's own pause menu, not a renderer of ui.pak's: `game_api.menu_native` tells `menu.c` where its mailbox (the usual `menubox.h` block) and the helper's words are, the Lua helper's pause-menu half (`src/games/luahelper/lh_menu.c`, two more hooks) serves the mailbox from the pause menu's frame, and a Lua glue (`lh_glue.lua`, which `build.sh` puts into `luahelper_bins.c` and the core sends each pause's VM as a request of target MENU) shows qwark's pages on the game's Cheats screen behind a TRAINER row in place of Help. It works under RPCS3 too, with LUA_PATCH's patch. The simulator links its games; its stdin `modules on` and `fakemodule` stand modules in for them (`test/test_gamemod.c`, the smoke run's "game modules").

Do not override `CELL_SDK`. Delete the `.prx` and `.sym` leftovers after a build. The compiler is ppu-lv2-gcc 4.1.1: gnu99 only, no C11, no `_Static_assert`, no anonymous unions, no floating-point printf (`printf2` from `printf.c` handles integers and strings only).

Host: `./build-host.sh` from Git Bash, or `build-host.bat` from Windows, builds both
PC executables (`build-host.sh host` or `build-host.sh rpcs3` for one of them):

- `qwark-host.exe`, the simulator the PC client is developed against, over a fake
  console driven from stdin (`src/plat/host/backend_fake.c`)
- `qwark-rpcs3.exe`, the same core over RPCS3's PINE IPC server
  (`src/plat/host/backend_pine.c`). Code patches are refused there, see the README.

Both link `src/plat/host/plat_host.c`, which holds everything that is not the game.
The build uses

```
C:\ghcup\ghc\9.4.7\mingw\bin\clang.exe   (x86_64-w64-windows-gnu; link -lws2_32 -lwinmm -lpthread)
```

The savefile helper (`src/games/sfhelper/`) is PowerPC code that runs inside the *game*, built by `make sfhelper` into the committed `src/games/sfhelper_bins.c`. It needs the SDK; a plain `make` rebuilds it only when a source is newer, and the host builds compile the committed file. Since build 56 the SPRX links only the helpers' numbers out of that file (their caves and hook words are under `#ifdef QWARK_EMULATOR`, for SAVEFILE_PATCH, the presence look and the tests): a console installs the helper out of `ui.pak` (below), and `build.sh` writes the helpers' identity in the pak, `SF_PAK_ID`, into `sfhelper_bins.h` with `pak.py --sf-id`. The code switches (`src/games/switches/`, the trampolines that let the code-writing toggles work under RPCS3) are built the same way by `make switches` into the committed `src/games/switches_bins.c`, which only the host builds link; the pieces named `own_*`, which a console writes itself (Deadlocked's HUD colours since revision 1.24), also go into `src/games/switches_own.c`, which the SPRX links too. A switch whose site is also a game's fingerprint site must keep its branch word, or the fingerprint must go on accepting the old one: an RPCS3 patch from an older build would otherwise leave the game unrecognised. The console menu's renderers (`src/games/menuhelper/`, revision 1.22: a shared core, `mh_core.c`, and a shim per game behind `mh_shim.h`) are built the same way again, by `make menuhelper` into the committed `src/games/menuhelper_bins.c`, which only the host builds link: since build 55 the module carries no renderer, and `make` packs that file into `ui.pak` beside `qwark.sprx` (`src/games/menuhelper/pak.py`, Python), which the module reads from `/dev_hdd0/qwark/ui.pak` (`src/core/uipak.c`, PROTOCOL.md 9.10) and accepts only with its own build, `MH_PAK_ID`, the renderers' CRC that build.sh writes into `menuhelper_bins.h`, and `SF_PAK_ID`, the savefile helpers', which the pak has carried since build 56 (format 2; without the pak a console's savefile actions answer BUSY with SAVEFILE_ERR_NO_PAK). `pak.py` is a source of both builds, so an edit to it regenerates both `*_bins.h`. `test/run.sh` and `test/smoke.py` pack the pak into their fake HDDs. `python -I src/games/menuhelper/check.py` checks the result against the executables and the mod libraries, and the pak against the table, and needs no SDK. `make pkg` packs `qwark.sprx` and `ui.pak` into `qwark-installer.pkg`, a homebrew app (`installer/`, title `QWRK00001`) that installs them on a console with no PC (docs/installer.md): its EBOOT is built with the SDK and signed by `scetool`, and `installer/pkg.py` writes the package itself, because the SDK's packager takes neither; never run `make_package_npdrm --extract` on it, which writes for ever. Its install logic is host-tested by `installer/test/run.sh`, which `test/run.sh` runs. `make dist` copies `qwark.sprx`, `ui.pak`, `qwark-installer.pkg` and `qwark-rpcs3.exe` into the committed `dist/`, which is where the client's release packaging takes them from.

Host tests: `./test/run.sh` builds and runs the unit tests against the host platform.
Integration: `python test/smoke.py` starts `qwark-host.exe`, drives its fake console over
stdin, talks the real wire protocol to it and prints PASS/FAIL per step; it then does the
same to `qwark-rpcs3.exe` against the fake PINE server in `test/fake_pine.py`.

## Rules

- Only the tick thread in `src/core/session.c` calls `plat_mem_read` / `plat_mem_write`. Network threads post commands to the ring.
- Nothing under `src/core/` or `src/games/` includes a PS3 header; everything platform-specific goes through `src/plat/plat.h`.
- Anything that writes an instruction word first asks `plat_can_patch_code()`. It is 0 under RPCS3, which recompiles PPU code, so patches, WRITES_CODE features, mods and the games' embedded helpers are refused there rather than half-applied. SessionInfo flags bit2 tells the client.
- Code that only matters where code patches are refused (the RPCS3 patch ops, the presence looks, the code switches) goes under `#ifdef QWARK_EMULATOR`, which `build-host.sh` and `test/run.sh` define and the makefile never does, or behind `!plat_can_patch_code()`, a constant 0 on the PS3; the SPRX runs where memory is tight and carries none of it.
- Static tables, no `malloc` and no `sys_memory_allocate` anywhere: the module asks the console for no memory after it has loaded. Stack budgets: 16 KB tick thread, 16 KB per client thread, 8 KB accept thread, so no large locals. The sizes are measured, not guessed — `src/plat/ps3/qwark_ps3.h` says how.
- Every multi-byte integer on the wire is big-endian; the PS3 is big-endian, the host is not, so use the `be16`/`be32`/`be64` helpers everywhere.
- Game knowledge (addresses, patch words, planet names) lives only in `src/games/<game>*`. A game may split into `<game>.c` (numbers, hot block, descriptors, vtable), `<game>.h` (the address table and the seam) and `<game>_panel.c` (the handlers), as RaC1 does. `classic.c` holds only what all four games genuinely share.
- Do not commit or add attribution trailers unless asked.
