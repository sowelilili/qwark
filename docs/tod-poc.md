- **LUA_EXEC's reply** has no `u16 st` of its own: the frame's status is the wire status, and the payload starts at `s32 lua_status` (a 12-byte head). - **LUA_STATUS** has two pad bytes after `err_len` (an 88-byte head), so `err` starts aligned; `installed` 2 is RPCS3's "not looked yet".

- **The PoC rows** (`tod_rows`, section 3) are not DESCRIBE features: ids 0 to 3 are reserved for them, the client's Lua box sends rows 0 and 1 through LUA_EXEC, and planets load through PLANET_LOAD (`tod_planet_load`, which writes `0x1006E764` only with `g_gameState` 4, a level object, and no request pending).

## 1. The mailbox protocol

### 1.1 Where things are

| what | address | size | notes |
|---|---|---|---|
| the helper (code) | `0x867360` | 1,316 bytes (`0x867360..0x867884`) | the code segment ends at `0x867360`; the cave runs to the page end `0x870000` (36 KB) |
| the mailbox (RW) | `0x8CA000` | `0x2600` (9,728) bytes | the RW segment ends at `0x8C9A08`, its TLS image at `0x8C9BF8`; the page ends at `0x8D0000` (24 KB) |
| VM hook | `0x4C461C` | 1 word | `bl CGameplayLuaVM_update` (`0x4BDCC909`) becomes `bl 0x867360` (`0x483A2D45`) |
| error tap | `0x68F8F8` | 1 word | `CLuaVM_reportError`'s lone `blr` (`0x4E800020`) becomes `b 0x867478` (`0x481D7B80`) |
| the gameplay `lua_State*` | `0x102043D0` | u32 | `g_gameplayLuaVM` (`0x102043CC`) + 4; 0 between levels |

Both caves are past their segment's bytes but inside its last 64 KB page, so they exist only if lv2 (and RPCS3) map whole 64 KB pages. `check.py` confirms everything that can be confirmed from the file; the mapping is live check 2.

### 1.2 The block

Everything is big-endian. Each field has one writer.

| off | field | writer | meaning |
|---|---|---|---|
| 0x000 | u32 `magic` | qwark | `'QLUA'` (`0x514C5541`). The helper does nothing without it |
| 0x004 | u16 `version`, u16 `size` | qwark | 1, `0x2600` |
| 0x008 | u32 `req` | qwark | sequence number of the latest request |
| 0x00C | u32 `ack` | helper | the last sequence number answered |
| 0x010 | u32 `cancel` | qwark | a sequence number qwark withdrew |
| 0x014 | u32 `busy` | helper | the request the helper is inside, else 0 |
| 0x018 | s32 `status` | helper | below |
| 0x01C | u32 `chunk_len` | qwark | bytes of source in `chunk` |
| 0x020 | u32 `out_len` | helper | bytes of text in `out`, before its NUL |
| 0x024 | u8 `out_type`, u8 `out_flags` | helper | Lua 5.0 `lua_type` of the first result (0xFF none); bit0 TRUNCATED, bit1 TRUE (a true boolean) |
| 0x028 | u32 `heartbeat` | helper | +1 on every gameplay frame |
| 0x02C | u32 `last_state` | helper | the `lua_State*` the last frame saw |
| 0x030 | u32 `err_seq`, `err_vm`, `err_len` | helper | the error tap: +1 per error the game reports, which VM, how long |
| 0x040 | char[64] `err_script` | helper | `g_luaCurrentScriptName` at the time |
| 0x100 | char[256] `err` | helper | the game's error text, `"<kind> Error - <message>"` |
| 0x200 | char[1024] `out` | helper | the result as text, or the error message |
| 0x600 | char[8192] `chunk` | qwark | Lua source (or big-endian, float-number bytecode) |

qwark polls the first 0x40 bytes in one read.

### 1.3 The sequence

**qwark sends** only while `req == ack`, or while `cancel == req` (its own withdrawn request): `chunk`, then `chunk_len`, then `req = req + 1` last.

**The helper**, on every gameplay frame, right after the game's own `CGameplayLuaVM_update` (REPORT 2.3: no coroutine running, the gameplay allocator current, the level up; never on a paused frame, in a menu or during a load):

1. nothing at all unless `magic` is right; `heartbeat += 1`; `last_state = L`;
2. `r = req`; nothing more if `r == ack`;
3. `busy = r`; `sync`;
4. `cancel == r`: status CANCELLED, the chunk is not read; `L == 0`: NO_STATE; `chunk_len` 0 or over 8192: BAD_LEN;
5. otherwise: `LuaAlloc_setCurrent(&vm->alloc)`, `top = lua_gettop(L)`, `luaL_loadbuffer(L, chunk, len, "=qwark")`, then `lua_pcall(L, 0, 1, 0)`; the first result (or the error message either call pushed) as text into `out` when it is a string or a number, its type into `out_type`; `lua_settop(L, top)`; the previous allocator back;
6. `out_len`, `out_type`, `out_flags`, `status`; `sync`; `ack = r`; `sync`; `busy = 0`.

**qwark waits** for `ack == req`. When `LUAMB_T_ANSWER_MS` (1.5 s) passes first, it **withdraws** the request: it writes `cancel = req`, then reads the header again.

- `ack == req` now: the answer came in between; it is the answer.
- `busy != req`: the helper is not inside the request. Since the helper raises `busy` *before* it reads `cancel`, any later look at the request finds the cancel: it can never run late. The slot is free at once. A request sent next simply overtakes it.
- `busy == req`: the helper is in it, or about to find the cancel, and its `ack` follows within the same frame. qwark keeps the slot (CANCELLING) until that ack, and refuses new requests (BUSY) meanwhile. After `LUAMB_T_HUNG_MS` (5 s) of that, it calls the game hung: a chunk that loops forever hangs the game's thread, and nothing can stop it.

The timeout is reported as **NOT_RUNNING** when the `heartbeat` did not move since the send (no gameplay frame ran: paused, a menu, a load, the XMB), and **TIMEOUT** when frames ran.

**On every attach** qwark withdraws whatever request an earlier session left outstanding (`luamb_attach`), for the same reason: a request the user made minutes ago must never fire now. The speedrun rule (auto-applied writes are opt-in, DESIGN 3.7) is what drives this design.

### 1.4 Status codes

| value | name | from | meaning |
|---|---|---|---|
| 0 | OK | Lua | ran; `out` is the first result as text |
| 1 | ERRRUN | Lua | a runtime error; `out` is the message (`qwark:1: ...`) |
| 2 | ERRFILE | Lua | (never from a buffer) |
| 3 | ERRSYNTAX | Lua | the chunk did not compile; `out` is the message |
| 4 | ERRMEM | Lua | the gameplay heap is out (3 MB fallback heap) |
| 5 | ERRERR | Lua | an error in the error handler (none is set) |
| 0x100 | NO_STATE | helper | `L` was 0 |
| 0x101 | BAD_LEN | helper | `chunk_len` 0 or over the cap |
| 0x102 | CANCELLED | helper | withdrawn before it ran |
| 0x103 | NO_ROOM | helper | revision 1.29, target MENU only: the pause menu's Lua pool is short even after a collection (docs/tod-menu.md 10) |
| 0x200 | TIMEOUT | qwark | frames ran but no answer in time |
| 0x201 | NOT_RUNNING | qwark | no gameplay frame ran in time |
| 0x202 | HUNG | qwark | the helper has been inside a chunk past the hang limit (a client-side state, see 2.1) |

### 1.5 The error tap

The game's `CLuaVM_handleResult` (`0x68F7A0`) formats every error a level script raises as `"<Runtime|Syntax|File|Memory Allocation> Error - <message>"` and hands it to the virtual `reportError`. Both VMs end in `CLuaVM_reportError` (`0x68F8F8`, a lone `blr`): the config VM's vtable slot points there directly, and the gameplay VM's `CGameplayLuaVM_reportError` (`0x290B70`) calls it through the cross-TOC trampoline `0x268610` (check.py follows both). The tap replaces that `blr` with a plain branch into the helper (`lh_err_tap`), which copies the text and the running script's name into `err` and `err_script`, sets `err_vm` and `err_len`, `sync`s and bumps `err_seq`, and returns to the game's caller. So the game's own script errors, which retail drops on the floor, now reach qwark.

A chunk qwark sends does not go through `reportError`: its error comes back in `out` with status 1 or 3. Errors raised inside coroutines the chunk starts, and inside level scripts the chunk wakes (`run_script`), arrive through the tap on later frames.

### 1.6 Why the helper looks the way it does

- **Three TOCs.** The hook site and `CGameplayLuaVM_update` are in the middle TOC range (r2 `0x8BB068`), every Lua function in the top one (`0x8CB054`). The entry (`lh_entry.S`) keeps the caller's r2 in its frame, calls the update with it, sets `0x8CB054` for the C part and puts the caller's r2 back: the instruction after the hook site is a `nop`, so the game expects r2 unchanged. Calls within the Lua range are followed by `nop`s too, so r2 survives every call the C part makes. `check.py` checks every function's descriptor TOC.
- **No data, no strings, no TOC** in the helper, as in the savefile helper; the chunk name `"=qwark"` sits in the code cave beside the entry.
- `lua_tostring` is asked only of strings and numbers, so it never converts anything in place that the game would see; the stack is put back exactly with `lua_settop`.
- Lua is never entered outside `lua_pcall` (REPORT 2.4: an unprotected error is `exit(1)`). `luaL_loadbuffer` is protected internally (`luaD_protectedparser`).

## 2. LUA_EXEC, as it should land in phase 2

### 2.1 The ops

**The numbers.** The game modules (revision 1.26, build 57) took one opcode, **GAME_MODULE 0x0008**, a control op, and SessionInfo `flags2` bit5 GAME_MODULE_BAD and bit6 GAME_WAITING (bit4 is DEV, bit0 USB_MODS). As of build 57 the whole `0x00C0` and `0x00E0` blocks are unused in `proto.h`, after the manips' `0x00D0..0x00D3`, so the Lua ops take **`0x00E0..0x00E2`** as below, and phase 2 writes them into `proto.h` and PROTOCOL.md under a revision of its own (1.27). Nothing in the module work changed the reply layouts or status codes these ops reuse.

**LUA_EXEC (0x00E0).** Request: `u16 len, u16 flags (0), char src[len]`, len 1..8192. The network thread posts it to the tick thread, which runs `luamb_send` and then `luamb_poll` once a tick until it gives an answer, and replies:

```
u16 st          ST_OK when the exchange finished (whatever Lua said), else below
u16 pad
s32 lua_status  section 1.4
u32 seq
u8  out_type    Lua type of the first result, 0xFF none
u8  out_flags   bit0 TRUNCATED, bit1 TRUE
u16 out_len
char out[out_len]  no NUL
```

Wire status `st`:
- `NOT_INGAME` outside a game, and **`NOT_FOUND` when the game has no `lua_State`** (`0x102043D0` is 0: between levels, the main menu, a load). That is answered at once, with nothing written: there is no queueing across a level change.
- `UNSUPPORTED`: the running game has no Lua helper, or the helper is not in (no magic; on RPCS3, the patch not applied).
- `BUSY`: a request is outstanding or being withdrawn (CANCELLING), including one from another client; also while HUNG, with `lua_status` HUNG.
- `BAD_ARG`: len 0 or over 8192.
- `IO_ERROR`: a memory access failed.
- `ST_OK` with `lua_status` TIMEOUT or NOT_RUNNING when the helper did not answer in 1.5 s. The request is already withdrawn then and will not run.

The reply waits at most 1.5 s plus a tick: the network thread blocks on the command like the other tick-thread ops do.

**LUA_STATUS (0x00E1)**, no request: `u8 installed (0 no, 1 yes, 2 unknown), u8 phase, u16 pad, u32 heartbeat, u32 state, u32 err_seq, u32 err_vm, char err_script[64], u16 err_len, char err[err_len]`. Answers in any session state with a game; it lets a client show the last script error and whether frames are running.

**LUA_PATCH (0x00E2)**, emulator builds only (QWARK_EMULATOR), exactly SAVEFILE_PATCH's layout (PROTOCOL 5.12.1): `lh_patch_build` already makes the reply. The words are the cave, then the mailbox's identity (`0x8CA000 = 0x514C5541`, `0x8CA004 = 0x00012600`), then the error tap, then the VM hook last; no single bytes (the mailbox is zero at load). 333 words today (329 of code), 2,676 bytes.

**Re-injection.** Once the game has arrived (item 7 below), qwark watches `0x102043D0` on the tick (one u32 read, or part of a slow hot block): a change to a new non-zero pointer is a new level and a fresh state, which is when persistent mods (SPEC 4.12) are sent again, following the auto-apply rules of DESIGN 3.7 (prompt on a same-session return, silent per-mod flag). A pointer that goes 0 cancels nothing by itself; the next LUA_EXEC answers NOT_FOUND.

### 2.2 What phase 2 must wire up

The module system phase 2 lands on is the one revision 1.26 built (PROTOCOL.md 9.11, `src/games/module.h`, CLAUDE.md "Game modules"). In a test build (`make`, `QWARK_GAME_MODULES=1`) the core links no game: each game is a module of its own, named for the game, which `src/core/gamemod.c` loads behind the memory gate once the game is INGAME and unloads when it quits. A release (`make release`) links the games into `qwark.sprx` instead. ToD is added the same way as the four, as a module first:

1. **The game id and the module name.** ToD is **game 5**: `GAME_TOD 5` in `proto.h` (SessionInfo's `game` byte, GAME_MODULE's `game`, the client's `GameId`). Its module is **`tod.sprx`**, a name of its own and never a number formatted into one; the name is one line in each of the tables that already name the four: the title index's `g_module_names` (`src/games/titles.c`, read through `title_module_name`; `gamemod_names` walks it up to the first gap, so the entry must be at index 5), the makefile's `GAME_MODULES` with `GAME_ID_tod = 5` and `GAME_SRCS_tod` (the static pattern rule builds it with `-DQWARK_MODULE_GAME=5`), the installer's `INST_GAME_NAME_5` with `INST_GAMES` 5 and `pkg.py`'s `GAME_FILES`, and the client's `GameModule` table and `packaging/game-module-names.ps1`. `.new` staging follows by itself (`tod.sprx.new`). FILE_OPEN's internal close flag keeps the game id in a nibble (`net.c`), which 5 fits.
2. **The title index entry** (`g_titles` in `titles.c`, resident in every build): `{ "NPEA00452" }`, `GAME_TOD`, the fingerprint `0x2EA5F0 = 0x93EB06E8` (`tod_facts`), no `fp_switch` (ToD has no code switches), `quit_hook_addr` 0 until a quit hook is known, the pad mask's address, no boot patches and no pause pair (nothing ToD does must happen in a boot's first seconds: the Lua helper installs on demand, item 6), and `LINKED(tod_game)` for the release build. The title index is what makes the session INGAME with `game` 0 and `flags2` bit6 while `tod.sprx` waits for memory.
3. **The game itself, `src/games/tod.c`, behind `core_api`.** It starts with `#include "core_import.h"`, as every game source does, and calls the core only through the names in `src/games/core_api.txt` (add any it lacks there and run `python -I tools/coreapi.py`; `test/run.sh`'s `coreapi.py nmcheck` holds the host objects to it). Its `game_api` (`tod_game`) is filled from `tod_facts`: the hot block (one read of 0x5C bytes at `0x10691918`; `tod_pad_to_og` for the mask), planets (`planet_load` = one s32 write to `0x1006E764`, section 3), positions through the 3-read chain, the inventory as plain reads and writes (bolts, raritanium, weapons, cheats; never through Lua).
4. **No writable statics: the lent state area.** A module has one R-X segment and nothing writable (`tools/gamemodule.py objs` and `check` refuse a writable section, bss, TLS or an import; at most 61,440 bytes). `tod.c` today has only `const` tables, so it fits as it is; anything mutable phase 2 adds goes into one `struct tod_state` reached as `QWARK_STATE_AT(struct tod_state, QWARK_STATE_GAME_OFF)` behind a `T->` macro in a module and a static in a linked build, held to `QWARK_STATE_GAME_MAX` (2,048 bytes of the 6,144-byte area) with the same `typedef char ..._fits[...]` the four use. The core zeroes the area before every load, so `init` sets it up each time. `luahelper_bins.c`'s bytes are `const` and may sit in the module's R-X segment, but they count against its page.
5. **The module's start, `src/plat/ps3/game_module.c`.** It names the vtable it hands back by pasting `rac` and `QWARK_MODULE_GAME` (`rac1_game` .. `rac4_game`), which does not give `tod_game`; phase 2 passes the vtable's name from the makefile (a `GAME_VTABLE_<name>` beside `GAME_ID_<name>`, as `-DQWARK_MODULE_VTABLE=tod_game`) rather than renaming ToD's vtable to fit a number. The stamp `gamemodule.py check` looks for carries game id 5 unchanged.
6. **A `game_api` slot for Lua** (SPEC 4.12): `lua_desc()` returning the `lh_desc`, so the core's LUA_EXEC stays game-agnostic and works the same whether ToD is linked or a module. The mailbox's state machine (`luamb.c`) is the core's, with its statics in the core, not in the lent area: it outlives a module's load and unload, and `luamb_attach` withdraws a request an earlier session left whatever the module did.
7. **The core op** in `net.c`/`session.c`: LUA_EXEC and LUA_STATUS on the tick thread with `luamb.c` and `struct luamb_io` bound to `mem_read`/`mem_write`; `luamb_attach` when the game *arrives* (`gamemod_tick` answering `GM_ARRIVED_GAME`, which for a module is `game.window_ms` or more after INGAME), not at INGAME entry. While the game is not in, every game op answers UNSUPPORTED (PROTOCOL.md 9.11), and so do these. Every network-thread use of `session_game()` takes the core lock and copies what it needs before letting go (the lock audit): `lua_desc()`'s answer is the module's memory and goes when it unloads.
8. **The install.** On a console, `lh_install` on the first LUA_EXEC (or as the game arrives, behind a config key like `savefile_helper`), after `plat_can_patch_code()`. On RPCS3, `lh_present` once a session (the savefile helper's presence rule), LUA_PATCH for the client, and `CHECKING` until the look is done. `qwark-rpcs3.exe` links its games like a release, so on RPCS3 none of this waits for a module.
9. **The bytes on a console: `ui.pak` kind 3.** The pak's entry layout fits the helper as it is: one code cave, and two hook words with the game's own words (so it can be taken out again). The header has no slot for a third identity, though (24 and 28 are the renderers' and the savefile helpers'), so this needs **pak format 3**: a 36-byte header with `LH_PAK_ID` at 32, or one CRC over all kinds. That is a change to `pak.py` and `uipak.c`, the core's, so it is proposed here rather than done. Until then `luahelper_bins.c` keeps its bytes under `QWARK_EMULATOR`, like the savefile helper's, or in `tod.sprx`'s R-X segment (item 4).
10. **The makefile**: `luahelper` and `luahelper-if-stale` targets calling `sh src/games/luahelper/build.sh [--if-stale]`, added to `all` beside `sfhelper-if-stale`. The core links `luamb.c` (3.0 KB of text with `-Os`, measured with ppu-lv2-gcc) in every build; `tod.sprx` links `tod.c` and, for the install half, `luahelper_patch.c` (2.3 KB; the patch builder goes under `QWARK_EMULATOR`) and `luahelper_bins.c` (0.2 KB). A release links them into `qwark.sprx` (`PPU_SRCS` under `QWARK_GAME_MODULES=0`, beside `rac4.c`), which grows the release module by ToD's whole size: whether a release carries ToD at all before modules ship in releases is the user's call.
11. **The client**: `GameId.Tod` (DisplayName "ToD") and `tod.sprx` in `GameModule`'s table (the send, the installs and the update's `.new` follow it), a Lua console (send a chunk, show `out`), the error tap's last message, and writing the RPCS3 patch from LUA_PATCH like the savefile helper's.
12. **`PROTOCOL.md`**: revision 1.27 with the ops above, the status codes, `tod.sprx` in 9.11's table of modules, and the mailbox for information (like 9.x).
13. **Later, `game-lua`**: `tod_facts` becomes the per-title data file (SPEC 4.12) unchanged in shape; `lh_tod.h` stays the helper's build input.

## 3. The PoC features (`tod.c`, `tod_rows`)

| id | kind | label | does |
|---|---|---|---|
| 0 | ACTION, Lua | Lua test (version, half speed) | `time_set_scale(0.5) return _VERSION`: answers `Lua 5.0.2` and the whole game runs at half speed |
| 1 | ACTION, Lua | Lua: normal speed | `time_set_scale(1) return _VERSION` |
| 2 | ENUM, write | Load planet | the LEVEL_ id as an s32 to `0x1006E764` |
| 3 | ENUM, Lua | Load planet (Lua) | `set_level(%v, true) return get_level()`, `%v` the id |

**The bindings** (all checked in Ghidra):
- `time_set_scale(number)`: tolua wrapper `0x2D5748` → `Lua_time_set_scale(double)` `0x2956F4`, which stores the value as a float to `g_gameClock+0` (`0x1074DDA8`). No hero handle, no arguments to get wrong, and an effect nobody can miss; row 1 undoes it.
- `set_level(number, boolean = true)`: wrapper `0x2B2DD0` (the boolean is optional, default true) → `Lua_set_level(level, force)` `0x291D80` → `LoadLevel(level, force, 0)` `0x2EA574`.
- `_VERSION` is the base library's.

**The planet load is `0x1006E764`, the pending request, not the save field.** The user's caution was right about the legacy address: old RaCMAN's `savePlanetId` `0x1029C55B` is the low byte of `g_saveData+0x906E8` (`0x1029C558`), the save's current level, which only ever records a load (writing it alone loads nothing). `0x1006E764` (`g_planetLoadRequest`) is different, from the decompile:
- `LoadLevel` (`0x2EA574`): when `g_gameState` (`0x10387F4C`) is 4, it stores the level in `0x1006E764` and returns; otherwise it writes the save field and calls `RequestLevelLoadState` itself.
- `LoadLevel_ProcessPending` (`0x2EA498`, polled from `Game_UpdateFrame`): while `0x1006E764 != -1`, it starts a screen fade; when the fade is done it writes the save field, calls `RequestLevelLoadState` and puts -1 back.

So the write is exactly what the game's own scripts do, fade and all, and row 3 lands in the same word during gameplay. Phase 2 should write it only while `g_gameState == 4` and the state pointer is non-zero, and never take it back once written (mid-fade that would leave a fade with no load).

**Not through Lua** (the user's steer): unlocks, bolts and anything a readout shows. `tod_facts` holds them as fixed addresses (with their marks in `tod.c`): bolts `0x1020C28C`, raritanium `0x1020C290`, the 32 weapon slots at `g_saveData` (`0x1020BE70`, 0x14 each, owned byte +0x10), the vendor unlocks at `0x102115C4`, the 14 extras (CHEAT_) at `0x10214568`.

## 4. Building and checking

- `sh src/games/luahelper/build.sh` (Cygwin, SDK on the PATH) rebuilds the helper and regenerates `luahelper_bins.c`/`.h`. It refuses unexpected sections, a helper past its cave, a mailbox past its page, and computes both hook words from the linked ELF.
- `python -I src/games/luahelper/check.py` checks it against the executable, no SDK needed (all 36 checks pass today): md5 and fingerprint; both hook words, the call target, r3's TOC slot (`0x8C1E4C = 0x102043CC`) and the `nop` after the call; the error tap's reach from both vtables; every called function's descriptor TOC; the bodies of `LuaAlloc_setCurrent` (stores to `0x10740DA8`), `luaL_loadbuffer` (calls `lua_load`) and `lua_pcall` (calls `luaD_pcall`); the caves outside every segment's bytes and inside its page; nothing in the executable referring to the helper's bytes or the mailbox (the top range's r2 `0x8CB054` lies inside the RW page, so its descriptor words are excluded, and no r2-relative access reaches past the TOC); and the helper's own branches.
- `python -I src/games/luahelper/check.py --yml PPU-<hash>` also prints the RPCS3 patch, ready to paste into a patch file, for a live test before phase 2's client support. The hash is the one RPCS3 logs as `PPU executable hash:` when it boots the game.
- `test/run.sh` builds `test/qwark-test-tod.exe` (124 checks).

## 5. Live checks, in order

Do these on RPCS3 first (nothing to install by hand on the game but a patch), then on the console. Read with any memory tool (the RaCMAN client's memory viewer, or `qwark-rpcs3` over PINE); none of these needs a write except the ones that say so.

1. **The state pointer and the load request.** In a level read `0x102043D0` (non-zero) and `0x1006E764` (expect `0xFFFFFFFF`). Load another planet the normal way and watch `0x102043D0` go to 0 and back to a new value, and `0x10387F4C` (expect 4 in gameplay). Then, in gameplay, write `0x00000002` to `0x1006E764`: expect a fade and a load into Stratus City, and `0x1006E764` back to -1. Repeat while paused and say what happens (the PoC assumes the request waits for gameplay).
2. **The caves are mapped and empty.** Read `0x867360..0x8678A0` and `0x8CA000..0x8CC600` at the main menu and in a level: expect zeros, and no read error. On RPCS3, also `0x86F000` and `0x8CF000` (the ends of the pages).
3. **RPCS3: the patch.** `check.py --yml PPU-<hash>` into a patch file of yours (the agents never write into the RPCS3 folder), enable it, boot, and look at RPCS3's log for `Unregistered PPU function` or a PPU exception at `0x8673xx`: **the code cave is past the end of the code segment, and whether RPCS3's recompiler or its interpreter fallback runs code there is the one real unknown of the RPCS3 path.** If it does not, the cave must move into dead code inside the segment (an unreferenced function of 1.4 KB; the search was started but not finished, and the switch-table code it found is not usable), and `lh_tod.h`'s `LH_CAVE` is the only line that changes. Then read `0x8CA000` (expect `0x514C5541 0x00012600`) and, in a level, watch `0x8CA028` (the heartbeat) count up at the frame rate, stop while paused, and `0x8CA02C` equal `0x102043D0`.
4. **The first chunk.** Write `return _VERSION` (15 bytes) to `0x8CA600`, `0x0000000F` to `0x8CA01C`, then `0x00000001` to `0x8CA008`. Expect `0x8CA00C` = 1, `0x8CA018` = 0, `0x8CA024` = 0x04, `0x8CA020` = 9 and `Lua 5.0.2` at `0x8CA200`. Then the PoC row: `time_set_scale(0.5) return _VERSION` as request 2, and the game at half speed; `time_set_scale(1)` as request 3.
5. **An error.** `error("x")` as the next request: status 1 and `qwark:1: x` in `out`. `this is not lua`: status 3.
6. **The error tap.** Harder to provoke on purpose; `run_script("no_such_script")` may raise one in the game's own code. Watch `0x8CA030` (err_seq) and the text at `0x8CA100`.
7. **The hero handle** (REPORT 2.5's open question): `local t = {} for k, v in pairs(_G) do if type(v) == "userdata" then table.insert(t, k) end end return table.concat(t, " ")`. A hero handle in a global settles how Lua mods get at Ratchet.
8. **The planet through Lua**: `set_level(2, true) return get_level()` in gameplay: expect the same fade and load as check 1, and the result is the level you were on (the load is deferred).
9. **Memory**: `return gcinfo()` for the gameplay heap in KB (Lua 5.0 returns used and threshold).
10. **Death and checkpoints**: die, and see whether `0x102043D0` stays the same (REPORT 2.2: probably it does).
11. **On the console**, the same after a hand install (phase 2 does it): the cave bytes and the mailbox identity first, then `0x68F8F8 = 0x481D7B80`, then `0x4C461C = 0x483A2D45` last, all from `luahelper_bins.c`.

**What god ratchet was.** The old RaCMAN wrote `0x9A` (any non-zero byte) into the low byte of `g_heroProxyMobyHandle` (`0x1020BD48`), the handle of a remote-controlled proxy moby (`HeroProxyMoby_*`, probably the Visi-Copter's). While that word is non-zero `Hero_Update` drops the hero's damage and `Hero_registerAsTarget` takes him out of the enemies' target list. A fake handle there is overwritten or cleared by the real proxy moby's spawn and death, and the camera code tries to resolve it. Since 2026-10-27 qwark has both: God Ratchet (16) is that write, exactly, because speedrunners use the glitch, and Infinite health (9, God Ratchet before) is the game's own unused debug flag beside it, which drops the damage the same way with nothing else attached; enemies still attack. Neither covers a death plane or a fall.

**The three items left off the Unlocks panel** (2026-10-27, from the game's level scripts in `global_cached.psarc` and the executable). `OBJ_VERDIGRIS_UPGRADE` (12, text "Verdigris Sector Upgrade") is a ship part: Pirate Base's closing cutscene (`l08_s02_lmap_rt`, `enemies.lua`) gives it with `unlock_level(LEVEL_RYKAN_V)`. `OBJ_PRAXUS_UPGRADE` (13, "Praxus Sector Upgrade") is the "Quasar Displacer" a Grummel ship-part vendor in Zordoom Prison would sell for 2,000 bolts, with the mission "Buy Praxus upgrade"; Pirate Base's vendor sold the "Helios Shielding" the same way. Both vendors are `shippart.lua`, which neither level's `main.lua` loads, so the Praxus upgrade is never given and nothing that runs reads either: the galactic map's visitable test is the level's own unlock byte (`GalMap_isLevelVisitable`), `is_sector_visitable` always answers yes, and the pause menu lists neither. Cut content, then: the Verdigris one a write-only flag, the Praxus one unused. `OBJ_HEXAGONAL_WASHER` (14) is the plumber's joke at Sargasso (`lombax.lua`, "a 3 centicubit hexagonal washer"); owning it does nothing.
