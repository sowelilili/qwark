# Tools of Destruction's console menu: the game's own pause menu (revision 1.29, pending)

The trainer's console menu in Tools of Destruction (NPEA00452 v01.00, `EBOOT.ELF` md5 `df9d68ada99b3f44ffe798ce03a1549c`, game 5, `tod.sprx`), drawn by the game's own pause menu as the four original games' menus are: a **TRAINER** row in place of the pause list's Inventory row (Options' Help row until section 14), and qwark's pages on the pause's own list and its GAME OPTIONS screen (since the fourth console test, section 12; until then the Cheats screen). This file has the reverse engineering, the design, and the test lists for a console and RPCS3.

Read from the executable, the pause menu's data (`built/anark/pause/built.dat` in `global_cached.psarc`, its 28 compiled Lua 5.0.2 chunks decompiled) and Ghidra (DL-ghidra:/NPEA00452.ELF). **Its first console test crashed as the pause opened (section 9), and so did the test of that fix, in the game's Lua allocator (section 10); the third test (build 34e848e) ran without a crash, but the glue never found what it looked for, so Help stayed Help and the combo opened the plain pause (section 11), whose fix ran in the fourth test (build e44961c): the row was in, but its links were dead, its pages wore the Cheats screen's title and counter, and the game's own Cheats screen broke; section 12 has why and the rework, which ran in the fifth test (build 87a143a): it works, but the list's frame kept the size of the menu it was entered from, loads from the Trainer said busy, and Manips wanted a spacer; section 13 has why and the fixes, which have not run yet** (section 13.6). Confidence marks as in the other ToD reports: **high** read end to end; **medium** read, the effect in game inferred; **low** a lead.

It replaces the prototype of 2026-10-31 (commit 55ef029: a panel of its own drawn with `Text_Draw`/`Sprite_Draw` from a frame hook at 0x3C5CD8 and a pad hook at 0x5D144C, ui.pak kind 3, `menu.tod`). The prototype is gone: no renderer of ToD's is in ui.pak any more, `menu.tod` means nothing, and the two hooks are never written. Its findings about the HUD's drawing calls are in that commit's version of this file.

## 1. The pause menu (high)

- **The state.** Start in play reaches `Game_UpdateFrame`'s last test, `thunk_InputMapper_isPressed(g_gameInputMapper, 1)` at **0x4C5ABC**, once every earlier check has passed (no menu up, no load request, `thunk_Game_isPauseBlocked(0)` clear, `g_planetLoadRequest` -1, the level more than 120 frames old). It then calls `thunk_PauseMenu_request` (0x23BB4): `g_pauseMenuRequest` (0x101CB228, `/ToD/Anark/PauseMenuRequest`) filled, and an overlay queued on the state stack (`GameState_queueOverlay`, op 2, state 5).
- `PauseMenu_enter` (0x248B4) sets `g_pauseMenuState` (0x101CB218) to 1 and starts `PauseMenuLoadingThread` (0x24A60): it builds an `AnarkMenuSystem` (0x14B0 bytes, `/ToD/Anark/AnarkMenuSystem`, `AnarkMenuSystem_ctor` 0x654768) out of the pause's arena into **`g_pauseMenuSystem` (0x101CB220)**, loads the presentation, opens the menu package's bindings (`tolua_menu_open`) on its VM, sets +0x10AB (the next update starts the presentation) and leaves. `g_pauseMenuState` 2 and 3 are "up", 4 closing (`PauseMenu_close` 0x23C9C, which `exit_pause_menu` reaches), 0 none (`PauseMenu_exit` 0x24610).
- **The frame.** `PauseMenu_update` (0x2406C, `g_gameState` 5's update, main thread) calls `thunk_AnarkMenuSystem_update` at **0x242B0** (`bl 0x119D0`, then `ld r2,40(r1)`) with r3 = `g_pauseMenuSystem`, only in states 2 and 3. `AnarkMenuSystem_update` (0x653D30) makes the Anark VMs' allocator current (`AnarkMenu_luaAllocator` 0x653048 returns `g_anarkLuaAllocator`, 0x1073DC40), reads the pads (`Input_UpdatePads`), runs the presentation and its Lua, and forces a full GC every second.
- **The menu VM.** The system's **lua_State is at +0x106C** (`AnarkMenuSystem_getLuaState` 0x653BBC; set by `AnarkMenuSystem_startPresentation` 0x654DD4 from the Lua object at +0x1058). It is a new state for every pause (the arena is reset, so the address can repeat). Lua 5.0.2, the base, table, string and math libraries, the menu package (179 functions: `exit_pause_menu`, `get_num_cheats`, `set_cheat_state` ...), the Anark framework (`scene`, `Presentation`, `Node`, `Event`, `Color`, `LOC`), and `SetLocalizedText` (Lua source embedded at 0x100FA7A0: a number is a text tag, a string is shown as it is).
- **The config VM** (`g_configLuaVM` 0x101E7E50) is the tuning sheets' and is not the menu's; the galactic map, vendors and front end are other `AnarkMenuSystem`s with other callers of the update (0x360BC, 0x39A38, the loading thread), which the menu does not touch.

## 2. The pause menu's structure (high, from the decompiled chunks)

The presentation is a scene of slides; each screen's behaviour is a Lua chunk run with `self` the behaviour node, its methods assigned onto it (`self.handleSelect = function ...`), and the nodes it uses found by path properties (`this.parent.ScrollableList`).

- **`ListUpdater`** (the pause's lists, one behaviour): `SetupMenus` builds `self.menuData[menu][i] = { text tag, callback }`. MAIN_MENU_INDEX 1 is Mission, Quick select, Weapons, Inventory, Gadgets, Items, Options, Extras (space combat and arena levels have their own first rows). **OPTIONS_MENU_INDEX 2: Game options (45 is Help's tag...) — 1 Game options, 2 Controls, 3 Moves, 4 Help (`{45, self.onHelp}`), 5 Save, 6 Load.** EXTRAS 3: Skill points, Cheats, Concept art, Cinematics, Skins. `handleSelect` calls the row's callback; `ActivateItem` shows a row's label with `SetLocalizedText(item, menuData[i][1])`. `onHelp` is `scene:goToSlide(12)`, `onCheats` `scene:goToSlide(16)`; every screen's back is `scene:goToSlide(21)`, the list (`blankHandler`), whose activation puts the list back on its own slide (`currentSlide`: 3 main, 7 options, 9 extras).
- **`cheatHandler`** (slide 16, the Cheats screen): a `ScrollableList` (`listBehavior`, six visible rows `cheat1`..`cheat6`, each a `label` and a `value` text; it scrolls any count) driven by the handler's `getNumListItems`, `setListItemValue(i, item)`, `isSelectable(i)`, `onSelectedItemChanged`, `handleSelect`/`handleRight` (`changeCheatState(1)`), `handleLeft` (`changeCheatState(-1)`) and `handleBack` (slide 21); the list calls them through `self.listUpdater:...`, by name at every call. The screen's title is the text node `Page_name2` ("CHEATS"), its description `Description` (`itemDesc`), and `skillpoint_label`/`skillpoint_value` the counter. Its own values come from globals (`get_num_cheats`, `is_cheat_unlocked`, `get_cheat_name`, `get_cheat_state_name`, `get_cheat_desc`, `set_cheat_state` ...).
- The options screens (`optHandler`, `controlHandler`) are label/value lists too; the Cheats screen is the one whose rows are plain label and value text set from Lua, which is what qwark's rows are.

## 3. The design

```
qwark (C, src/core/menu.c)          menubox (0x8CD000)          the Lua helper (C, in the game)       the glue (Lua, pause VM)
 the pages, rows, values,  --post--> page, seqlock    --take-->  lh_menu.c: copy, rows,      <--qw()-- TRAINER row, Cheats screen,
 what a row does           <--ack--- events           <--post--  events, hstate, requests    --qw()--> presses, back, open/close
```

- **qwark's side is unchanged.** The menu's model, pages and rows (`menu.c`, ToD's `game_api.menu` in `tod_game.c`) and the mailbox (`menubox.h`, version 3) are every game's. ToD's mailbox is at 0x8CD000 (0x880 bytes: 32 rows of 0x40, either page type, caps STEPS | BACK | REQUEST, renderer 5). What is new for menu.c is only that the "renderer" is the game's own (`game_api.menu_native`, `struct menu_native`): no ui.pak entry, no cave and no hook of the menu's; its install is the game's Lua helper (`lua_core_helper_ready`) and a mailbox header menu.c writes itself; `menu.help` is a byte (0x8CE000); `menu.enabled` 0 clears the mailbox's identity.
- **The Lua helper's pause-menu half** (`src/games/luahelper/`, revision 1.29), C in the same cave as the gameplay half, two more hooks:
  - **0x242B0** (`bl 0x119D0` -> `bl .lh_menu_hook`): calls the update as the game did, then `lh_menu_tick(ms)` on the pause menu's lua_State with the Anark allocator current, **only on a frame `lm_ready` passes and with the pause's presentation pushed** (section 9): for a new VM it registers the C function `qw` and asks qwark for the glue (`LM_GLUE` WANTED, `LM_LOADS` + 1); it serves requests for the menu's VM (the Lua mailbox's target MENU, below); and it calls the glue's `qwark_frame` every frame under `lua_pcall` (an error goes to the Lua mailbox's err area as "qwark-menu" and stops the glue for that pause; LUA_STATUS shows it).
  - **0x4C5ABC** (`bl 0x2672E0` -> `bl .lh_pause_hook`): the pause test itself, then `lm_pause_check`: qwark's open request in play answers "pressed", so the game opens its pause exactly as for Start, past every check of its own, and the glue opens the menu in it.
  - **the pause menu's Lua pool** (section 10): before anything goes into the VM, the push included, the helper counts the blocks left in the game's Anark Lua pool, which faults when it runs out; with too few it makes the game's own full collection, and with too few after that it keeps out (a glue already in takes itself out, `qwark_quit`; a request is answered `NO_ROOM`). A frame that served a request does not also run `qwark_frame`.
  - `lh_menu.c` is the bridge's C, the same jobs as the four renderers' `mh_core.c`: the page copied out of the mailbox under its seqlock into a block of its own (0x8CE040), so the glue reads rows only from there; a press posted as an event with the shown page's key and the row's id, one in flight at a time; hstate and the frame count; the requests. A gameplay frame (`lm_gameplay_frame`) closes the menu (any way out of the pause) and makes the next pause a new VM. Host-tested on the PC (`test/test_tod_menu.c`).
- **The glue** (as it was until the fourth console test; section 12 has what it shows now and how it takes over) (`src/games/luahelper/lh_glue.lua`, about 7.8 KB once its comments and the spaces around its operators are out): **qwark sends it** to each new pause menu VM as a request of target MENU (`lua_core_menu_glue`, from menu.c's serve, once per `LM_LOADS`), because in the cave it would make the helper's RPCS3 patch (LUA_PATCH) bigger than a reply. It finds the two behaviours it needs by what they hold, not by name and without walking the scene, among the keys of `scene._table_ActDeactRegisters`, the table every behaviour that calls `self:_useOnActivateDeactivate()` in its onInitialize joins (AnarkLibraryExtensions: `scene._table_ActDeactRegisters = {}`, `scene._table_ActDeactRegisters[self] = false`), and since section 11 each apart: the `ListUpdater`, by the `menuData` row whose callback is its own `onHelp` in whichever menu holds it (the TRAINER row needs nothing else), looked for every tenth frame, then (after 30 looks, when it says LM_NOTE 2) every sixtieth for the rest of the pause; the behaviour with `changeCheatState` and `getNumListItems` (cheatHandler), looked for with it and, once the Trainer has gone to its slide, every frame for 90 frames, the page waiting for it (LM_NOTE 5 when it turns up there, 3 and back to the list when it does not). The combo needs only the scene (`scene`, else `Presentation.scene`) and `Node.goToSlide`. The tree walk that was the fallback is gone (section 10: every node it reached became a Lua object the game keeps). Nothing in the glue makes garbage frame after frame: no closure per call (`pcall(index, o, k)`, not `pcall(function() return o[k] end)`), no vararg function, and every wrapped function is kept beside the game's so `qwark_quit` can put them all back. The title and the counter are `cheatHandler.parent.shell_BG.Page_name2`, `.skillpoint_label` and the handler's own `totalSkillpoints`. Every Anark object is touched only if it is a userdata and only under `pcall`. It wraps, never replaces:
  - Options' Help row (row 4, wherever the look found it) becomes `{ "TRAINER", open }` while the Help byte is 1, the game's `{45, onHelp}` otherwise (checked to be Help before anything is touched);
  - `open()`: hstate open, then the Cheats screen (slide 16), as `onCheats` goes there;
  - while the menu is up, the handler's methods and the cheat globals answer from qwark's page (`qw(1, i)`): the label at the left, the value at the right (">" for a link), INFO rows not selectable, the title in `Page_name2`, qwark's last answer in the description; the cross posts ACTIVATE, Left/Right post LEFT/RIGHT on rows that step, Triangle posts BACK, or at qwark's root leaves to the list (slide 21); `changeCheatState` and `Node.goToSlide(21)` are caught too, for presses the game might route around the wrapped methods; of the cheat globals only those the screen's own remaining code calls are wrapped (`is_cheat_unlocked` from onUpdate and onSelectedItemChanged, `get_cheat_desc`, `get_current_skillpoints` from onActivate), the rest being reached only from the methods already wrapped;
  - every frame `qwark_frame` polls (`qw(0)`): a new key restarts the list with the cursor where qwark keeps it, new values refresh the visible rows, a request is taken (open; close leaves the menu and `exit_pause_menu()`), and with qwark gone (identity cleared) the menu leaves and Help is the game's again;
  - the cursor at the window's edge of a page longer than 32 rows posts SCROLL_UP/DOWN, as the renderers do.
- **The combo** (edge-triggered by qwark's combo arming, as for every game: one request per press, a held combo fires nothing more): menu closed -> REQ_OPEN; in play the pause test takes it (the pause opens, the glue opens the menu on its first frames once the pause has settled, 15 frames), in the pause the glue takes it; menu up -> REQ_CLOSE, which leaves the pause. A request nobody takes in 0.5 s is withdrawn by qwark as for every game; one the pause test took waits up to 30 gameplay frames for the pause to come up.
- **The Lua mailbox, version 2** (`luamb.h`): `target` (byte 0x26, qwark's: 0 gameplay VM, 1 the pause menu's) and `menu_beat` (0x3C, +1 every pause menu frame). The gameplay frame serves only target 0, the pause menu's frame only target 1; a MENU request's timeout reads `menu_beat`. LUA_EXEC's `flags` bit0 picks the menu's VM (NOT_FOUND with no pause up). The gameplay half is otherwise as it was.
- **C first.** Every value, label and decision is qwark's, in C; nothing polled goes through Lua (the glue's qw() calls read the helper's copy in the game's memory); the only Lua is what the game's menu system needs to show rows and hand back presses.

## 4. What is native and what is not

- Native (since the fourth console test, section 12): the pause menu, its Options list and its row; MAIN pages (the root, Unlocks) as a menu of that list, with its highlight, cursor, sounds and select; CONFIG pages on the GAME OPTIONS screen, its six rows, highlight box, header and description, Up/Down/Left/Right/cross/Triangle as the game binds them there, its sounds; the game's input, the game's own pause (no frozen clock, no pad blanking), Start/back behaving as the pause does.
- Not native: the rows' text is qwark's English labels in capitals, not localised; a link's value column on Game Options says ">"; a CONFIG page longer than six rows comes a window at a time; there is no slider (no ToD row has a range).

## 6. RPCS3

Supported, which none of the four originals' menus is: the menu needs no code of its own beyond the Lua helper, which RPCS3 takes as the LUA_PATCH patch at boot; the menu's mailbox, the help byte and the glue are data writes and a request over PINE. `qwark-rpcs3` installs the menu once it has found the patch (LUA_STATUS installed 1); without the patch the combo says "needs qwark's RPCS3 patch (Lua helper)". MENU_HELP answers OK in `qwark-rpcs3` now. The open question is the Lua helper's own live check 3 (docs/tod-poc.md 5): whether RPCS3 runs code in the segment padding at 0x867360.

## 9. The pause menu crash of the first console test (revision 1.29, pending)

**What the user saw** (build 57's test module, 2026-10-31): "lua: helper installed", "menu: the game's own menu served for game 5", and the game crashed as the pause menu opened, by Start and by the combo alike. The dump: `pc=0x79A388 lwz r3,0x20C(r3)`, r3 = 0, DATA_HTAB_MISS, under `AnarkPresentation_findElement` 0x79A588 <- `CLuaObject_getNumChildren` 0x76B604 <- `tolua_Node_getNumChildren` 0x7774C4 <- the Lua VM <- `lua_pcall` 0x692990 <- the helper (0x867C10, `lh_menu_tick`; 0x8673B8, `.lh_menu_hook`), r2 the helper's TOC. So the glue's `walk` called `scene:getNumChildren()` on the very first frame it looked.

**Why the object is NULL** (high, read end to end). A Node's Lua object (`CLuaObject`, 0x30 bytes) holds no pointer to its element: +4 its binding, +8 the menu system's Lua bridge (`AnarkLuaBridge`, `AnarkMenuSystem`+0x1058), +0xC the element's handle. Every lookup of the element (`getNumChildren`, `getChildByIndex`, a child by name in `__index`, `goToSlide`'s events ...) goes through `CLuaObject_getPresentation`, bridge+8, the presentation, then `AnarkPresentation_findElement(presentation, handle)`, which reads the presentation's element table at +0x20C (`AnarkPresentation_elementTable` 0x79A374, kind 0). Bridge+8 is set only by the Anark runtime's push: `AnarkRuntime_pushPresentation` (0x79647C, the runtime at `AnarkMenuSystem`+0x1068) puts the presentation on its deque (+0xAC, count +0xBC) and calls its push listeners with event 6, and the bridge's (`AnarkLuaBridge_onRuntimeEvent`, registered by `AnarkLuaBridge_ctor` for events 1, 2, 6, 7 and 11) stores it at +8 (`AnarkLuaBridge_onPresentationPush`, which also sets the Lua global `Presentation`); `AnarkRuntime_popPresentation` (0x79558C, event 7) clears +8 and `Presentation` again (`AnarkLuaBridge_onPresentationPop`). The runtime pushes a presentation only around its own work on it: each update (`AnarkRuntime_updatePresentations` 0x797650, from `AnarkMenuSystem_update`), each event (`AnarkRuntime_fireEvent`, `AnarkRuntime_sendToPresentations`), and the game's one call into it from outside an update, `AnarkMenuSystem_reset` (0x653B40: push, fire "reset", pop). The menu hook runs after `AnarkMenuSystem_update` has returned, where everything is popped, so bridge+8 is 0 and any Node method faults; a pcall cannot catch it. It is not the timing of the presentation's building (the glue's first look came in a frame where the menu was entirely built), not a userdata from another VM, nor an index past the children: no Node call can work at that point of any frame. Element properties such as `name` go another way (`CLuaObject_getElementDef`, the runtime's registry), which is why `get(n, "name")` came back and `getNumChildren` was the first call to fault.

**The fix.**
- **The helper** (`lh_menu.c` `lm_ready`, `luahelper.c` `lh_menu_tick`): nothing in the pause menu's VM unless the game's own words say the presentation is up: `g_pauseMenuState` 2 or 3 and `g_pauseMenuSystem` this system (PauseMenu_update's own test before the update), the system's lua_State, runtime, presentation and bridge set (`AnarkMenuSystem_startPresentation` sets them), `firstUpdate` (+0x10AB) clear (the loading thread's first update, `PauseMenuLoadingThread` 0x24A60, ran), `stopped` (+0x10A0) clear, `frames` (+0x10A4) 2 or more, and nothing pushed (the runtime's count and the bridge's presentation both 0, as after every update). Then it pushes the presentation exactly as `AnarkMenuSystem_reset` does, checks the push took (the bridge holds this presentation), registers `qw`, serves the menu's requests, calls `qwark_frame` under `lua_pcall`, and pops, every frame, so the glue runs where the game's own Lua does. A frame kept out says why in LM_WHY (`lh_menu.h` LM_WHY_*) and counts in LM_WAITS; qwark logs a wait of 300 frames once ("menu: the pause menu is not ready for the Trainer after N frames (why 0x..); Help stays the game's"). A request for the menu's VM waits for a frame let in, and times out as before if none comes.
- **The glue**: no tree walk to find its nodes (the registry, section 3), a bounded one only as the fallback (gone since section 10); every Anark object checked to be a userdata and every method called under `pcall`, with a missing argument passed as none (tolua refuses a `nil` it does not want); it gives up after 30 tries and says so (LM_NOTE 2, logged "found no Options list or Cheats screen; Help stays the game's"), and says when it is in (LM_NOTE 1, "the pause menu's glue is in: TRAINER in Options"). `qwark_frame` runs the frame under its own `pcall`: on an error it puts the game's Help row back and takes the menu down before handing the error to the helper, which logs it ("glue stopped on an error and put Help back"), clears `qwark_frame` and leaves the pause menu the game's for that pause.
- **check.py** holds every word of this to the executable (the push and pop as `AnarkMenuSystem_reset` calls them, the deque's count, the bridge's +8 in both listeners, `CLuaObject_getPresentation`, the menu system's words in `startPresentation` and `update`, `g_pauseMenuState` in `PauseMenu_update`); `test/test_tod_menu.c` the gate, reason by reason, and the log lines; the simulator's `fakepause wait` a pause that never comes up.

**The other assumptions, checked again against the decompiled chunks** (`built/anark/pause/built.dat`):
- `name`, `menuData`, `onHelp` (high). `name` is an element property every node has: the game's own `weaponHandler` reads `kid.name` of nodes from `getChildByIndex`, and `ScrollableList` reads `self.parent.name`. `menuData`, `OPTIONS_MENU_INDEX` and `onHelp` are fields the `ListUpdater`'s own chunk sets on its `self` (onInitialize, `SetupMenus`), the object `_table_ActDeactRegisters` holds as its key; the glue no longer depends on `getChildByIndex` handing back the same object (it does: `AnarkLuaCache_pushElement` returns the cached Lua object of a handle). There are two `ListUpdater` chunks (the mission list's and the pause list's); only the second has `menuData`. The element names (`ListUpdater`, `cheatHandler`) are confirmed by the data's paths `this.parent.ListUpdater` and `this.parent.cheatHandler`, but the glue no longer needs them.
- `handleSelect`/`handleBack` by name (medium-high). The presentation's data binds them as strings beside their events (`onSelectPressed` -> `handleSelect`, `onBackPressed` -> `handleBack`, `onLeftPressed` -> `handleLeft`, `onRightPressed` -> `handleRight`), and the methods only exist once the chunk has run, so the runtime can only find them by name when the event comes; the C++ dispatch itself is not read. The list's calls (`self.listUpdater:getNumListItems()`, `:setListItemValue`, `:isSelectable`, `:onSelectedItemChanged`) are by name in `ScrollableList`'s chunk (high), and so are the handler's own (`self:changeCheatState(1)`, `self:setListItemValue(...)`), so wrapping those catches a dispatch that bound the first ones once. Of the cheat globals, only `is_cheat_unlocked`, `get_cheat_desc` and `get_current_skillpoints` are still called by the screen's unwrapped code; the glue now wraps only those (the others were dead weight, and the fix would have pushed the glue past a request's size).
- Slide 16 straight from Options (high). `onCheats` is `scene:goToSlide(16)` from the list's `handleSelect`, the same call the TRAINER row's callback makes from the same `handleSelect` (the row's `[2]` called with the ListUpdater as `self`); the Cheats screen's `onActivate` (through the registry's `onUpdate`) and its list's reset follow the same way. Back is `scene:goToSlide(21)`, whose `blankHandler` sends the `ListUpdater` back to its `currentSlide`, 7 from Options (`doScreenChange(7, ...)`), 3 from the main list after the combo, so Triangle at qwark's root lands on the list the Trainer was opened from. `Node.goToSlide` is AnarkLibraryExtensions' Lua function (it fires a "set slide" event on the time-independent parent), which the glue captures after that chunk ran.
- Not changed: an open or close from the combo goes to slide 16 or 21 from `qwark_frame`, outside an update but with the presentation pushed, as `AnarkMenuSystem_reset` fires its event; the game's own handlers already call node methods right after `goToSlide` (`onMenuBack`, `doScreenChange`), so an event fired within a push does not end it.

**The pool** (high, read end to end). Every Anark VM allocates from `g_anarkLuaAllocator` (0x1073DC40, `AnarkMenu_luaAllocator`, which `AnarkMenuSystem_update`, its input pass, `AnarkMenuSystem_startPresentation` and the loading thread all make current, and none restores). It is a `LUA::PoolAllocator` (`/ToD/Lua/LuaPoolAllocator`): +0 its descriptor, +4 its chunks (0x20 bytes each: blocks, free list, bytes, stride, bytes handed out, count), +8 a heap, +0xC the class a size starts at, one int per 4 bytes. `Memory_InitHeaps` (0x6534A0) sets it up afresh at every pause (`PauseMenu_startLoading` 0x23D40, before the loading thread starts) from `g_anarkLuaPoolDesc` (0x100FA4A0): 18 classes, 4, 8, 16, 24, 32, 40, 48, 64, 72, 80, 96, 128, 160, 176, 192, 256, 384 and 640 bytes, 64 to 3,250 blocks each, 731 KB in all, plus a 1.25 MB heap; `Memory_FreeAnarkHeaps` (0x653364, from `PauseMenu_destroySystem` 0x23E04 at the pause's exit) releases it. `LuaPoolAllocator_alloc` takes a block from the size's class, or the next class up with a free block or blocks never handed out, and goes to the heap only for a size over 640 or one with no class. Its search runs `count - class + 1` chunks (`subf r3,r8,r10; addi r7,r31,1`), one past the table, and when every chunk before was used up it takes that one (`beq` at 0x6D39A0): the 0x20 bytes after the chunk table, which are class 0's first blocks. Its word +4, block 0's data, was 0x801B, taken for a free block and followed: the fault. r8 = 0x12 (chunk 18 of 18), r0 = 0x61D11000 (the chunk table) and r10 = 0x61D11240 (its end) in the dump say exactly that, and r6 = 4, the "count" at +0x14 (block 2's data, 3) plus one, was written into class 0's block before the fault. **So every class from 24 bytes to 640 was used up**: the pool had run out, and the game's allocator does not survive that.

**Why it ran out** (medium: the counts are read, the live numbers are not). Lua 5.0 collects when its byte count reaches twice what the last collection left, and `AnarkMenuSystem_update` forces one every second; neither knows the pool. The pool's classes are small (the 640-byte class has 150 blocks), and an object that finds its class used up takes a block from the next class up, a 20-byte upvalue a 640-byte block at worst, so it runs out long before Lua's count says the VM has grown. The helper's frame ran the glue's load (the parser's garbage: per function a constant table rehashed through every size and the code, line and constant arrays doubling, freed only by the next collection) and the glue's first look at the pause in one frame, and that look made a closure and two upvalues for every field it read (`pcall(function() return o[k] end)`), many hundreds of blocks, many more with the 400-node walk, whose every node also became a Lua object the game's element cache keeps. On top of the pause's own live set that used the pool up. It is not the allocator (r30 is the Anark pool, rightly current), not the stack (r1 0xD000F660; the game's own Lua runs deeper, from inside its update), not the glue's size (7,928 bytes taken by length, no NUL needed), and not the push (it allocates little; its listener sets the global `Presentation`).

**The fix.**
- **The helper counts the pool** (`lh_menu.c` `lm_room`, reads only, every link checked to be one of its chunk's blocks): blocks never handed out first, the free lists only as far as needed, from the largest class down, for a 20-byte object (its class, 24 bytes, and every larger one) and for the largest class alone. Before anything goes into the VM, the push included, it wants 1,024 and 16 (`LM_ROOM_SMALL`, `LM_ROOM_BIG`); for a request (the glue's load) 3,072 and 48. Short: the game's own full collection, `lua_setgcthreshold(L, 0)` (0x691504, as `AnarkMenuSystem_update` makes it at 0x653EC8), at the same point of the frame (after the update, nothing pushed; for a request, pushed, as Lua's own collections during the game's updates are), never under 128 and 4, where the collection itself might find no block. Still short: the frame is kept out (LM_WHY 0x080), the next collection waits 60 frames, LM_SHORT counts it and qwark logs it once a pause with what was left; a glue already in calls its `qwark_quit` (the menu down, the Help row and every wrapped function the game's again, so its objects are garbage the game gets back) and stops (LM_GLUE 3, LUA_STATUS's err "the pause menu's Lua pool ran short: the Trainer took itself out"); a request of target 1 is answered `NO_ROOM` (0x103), which qwark logs for the glue ("the pause menu's glue was not run ...").
- After a request ran in the VM the helper collects again if the pool is short of a load's room (the parser's garbage), and a frame that served a request does not also run `qwark_frame`: the load and the first look are never one frame's garbage.
- **The glue makes no garbage frame after frame**: `get`, `call` and `settext` pass a function and its arguments to `pcall` (no closure), the wrapped globals take fixed arguments (a vararg function makes an `arg` table every call), and the tree walk is gone: the registry has both behaviours (the pause's AnarkLibraryExtensions chunk builds it), and without them the glue gives up as before.
- **check.py** holds the pool's words to `LuaPoolAllocator_alloc`, the off-by-one, `LuaAlloc_realloc`'s path to it, `Memory_InitHeaps`'s setup from the descriptor and its classes, and the game's own collection; `test/test_tod_menu.c` holds `lm_room` (a fresh pool, the crash's state, freed blocks, a corrupt link, a released pool), the collections' floor and hold, and the log lines; the simulator's `fakepause short` and `fakepause tight` are a pause whose pool is short of a frame's room and of a load's (smoke.py too).

**What is not known**: how full the vanilla pause keeps the pool. If it is close to full without qwark, the helper keeps out of the VM and says so ("Lua pool is short even after a collection (N blocks left for small objects, M in its largest class)"), and the pause menu is the game's; the numbers in that line and in the "glue is in" line are what to tune `LM_ROOM_*` by. Making the pool bigger (its block counts in `g_anarkLuaPoolDesc`, read at every pause's `Memory_InitHeaps`) would be a data write, but it takes from the heap the pause's arena and frame arena share, which is not measured.

**The simulator's fake Lua** models neither the pool nor the allocator: it never runs the helper's C, only stands in for it. Checking "a menu VM call without the menu allocator current" there would test the stand-in, not the helper, and the allocator was right in the crash. `lm_room` and its decisions are the helper's own C, compiled for the PC in `test/test_tod_menu.c`.

### 13.3 Why a load from the Trainer said "busy" (high)

A planet row, a save file and Load set-aside are CLOSES actions (menu.c `defer`): qwark asks the menu to close (the glue takes it: the Trainer down, `exit_pause_menu()`), then runs the load once the game plays (`game_playing`: the pause's state 0 and nothing queued on the state stack). Tools of Destruction's pause goes away in two steps (`PauseMenu_update`'s state cases, `PauseMenu_update_stateCases` 0x24160): in state 4 (`PauseMenu_update_closing` 0x24174) it destroys the menu system and fades, and when the fade is done sets `g_pauseMenuState` 0; only the next frame, in state 0 (`PauseMenu_update_closed` 0x243F8), does it call `GameState_requestGameplay` (thunk 0x11690), which queues the move back to play. So for a frame or more the pause says 0, nothing is queued, and `g_gameState` is still 5. qwark's tick saw that often enough, ran the load, and `tod_planet_load` (and `tod_savefile_ready`) refused it: they want `g_gameState` 4.

### 13.4 Loads from the pause now

- **The wait** (menu.c `game_playing`): for a game whose menu is its own pause menu, the game back in play also means its game state is the play state (`struct menu_native` `play_state`, ToD's 4). A load the Trainer asked for runs on the first tick in plain play, never in the pause's last frames; the game's own gates stay as they were.
- **The client while paused** (session.c `session_planet_load` -> menu.c `menu_pause_defer`): a PLANET_LOAD while the pause is up with the glue in it (`g_pauseMenuState` 3, `g_gameState` 5, the glue loaded) is taken as a planet row is: answered OK, the pause closed, the planet loaded once the game plays. Elsewhere it goes to the game as before (BUSY in any other state). A SAVEFILE_RESTORE or LOAD_ASIDE from the client in the pause is still refused: the client follows a RESTORE's transfer to its end, and a deferred one would look finished to it; the Trainer's save files and Load set-aside do close the pause and load.
- **Closing the pause** (menu.c `native_defer_tick`): qwark's close request goes to the glue whether the Trainer is up or not (the glue takes requests once the pause's list is up), and is asked again while the pause is still up (a request nobody takes is withdrawn after half a second), and withdrawn once the pause is closing, so it never closes the next pause. The glue's close is the game's own Quit: `leave(false)`, then `exit_pause_menu()` (`MenuLua_exit_pause_menu` -> `PauseMenu_close`).
- **Cancelled** (logged "menu: ... was cancelled: ...", and on the console "Trainer: ... was cancelled: ..."): when the menu comes up again after its close (the player went on in the same pause), or when the game is neither in its pause nor in play (an FMV, the title) before it plays; and, as for every game, dropped five seconds on if the game never plays. The list is `tod.c`'s `tod_planets`, which PLANET_LIST, the Trainer's Planets page (`game_menu.planets` NULL: every planet) and the client all read. RaCMAN Reloaded's level-flag groups (`data/levelflags/tod.json`) and its test stand-in take the same names; its autosplitter route (`tod-planets.txt`) already named each planet both ways (`kortog,stratus`), so it was left alone and a route whose splits use either name still splits. The cutscene cache's own texts (Stratus City in its status and reasons) are unchanged.

### 15.2 A page at a time (high, from the code)

**Why it under-scrolled.** The CONFIG window slid as every renderer's does (`menu.c` `nav_move`, `window_at`): the cursor arriving at a window's last row asked for SCROLL_DOWN, and qwark put that row second from the top, so a six-row window moved four rows and the cursor jumped up. Up on the first window's top row wrapped inside the window (`lm_next`) to its last row, which then asked for SCROLL_DOWN: the "broken" Up.

**What it does now** (the game's own lists wrap: `ScrollableList.wrapIfNecessary` with `wrap` true, and Game Options' `changeSelection` from 1 to `max` and back):

- the mailbox's header carries **MBOX_CAP_PAGED** (`menubox.h` 0x20; ToD's LM_CAPS 0x2D; `native_install` writes a header with other caps again). With it, `menu.c` puts a long page in whole screens (starts 0, 6, 12, 18 for Planets' 19 rows; the last window short), and on SCROLL_DOWN shows the next with the cursor on its first row, on SCROLL_UP the one before with the cursor on its last, the first window's SCROLL_UP the last window and the last window's SCROLL_DOWN the first. A cursor that lands on a row it cannot stand on (a spacer, a status row) goes to the nearest one it can, the way the window turned first (`g_turn`). L1 and R1 (PAGE_*), where posted, move a whole window with the cursor on its row and stop at the ends. Without the bit everything is as before (the four games' renderers);
- the helper (`lh_menu.c` `lm_next`, `qw` operation 9) decides on the press: with the bit and a page longer than its window, it looks for a row the cursor may stand on between the cursor and the window's end that way; none, it posts SCROLL_DOWN or SCROLL_UP and the cursor stays until qwark's window comes; the glue then puts the cursor where qwark says (`oshow`), as for any new window. So spacers and status rows are skipped across a window's edge both ways. A page that fits wraps inside, as before;
- the glue's Game Options `changeSelection` no longer asks about the window's edge as the cursor arrives (`scroll`); only `lm_next` does. The pause's list (MAIN pages) still asks on arrival (`lm_edge`), but no MAIN page is longer than its nine rows (the root has six or seven, Unlocks five).

### 15.3 TRAINER from the first frame (high, from built.dat)

The list's rows get their text only in `ScrollableList.updateAllItems` -> `ListUpdater.setListItemValue` -> `ActivateItem` (`menuData[currentMenuIndex][i][1]` through `SetText`), which the list calls at its reset, its activation and every cursor move. The glue put TRAINER into the Inventory row's `menuData` entry after the list had drawn it, so the row read INVENTORY until the next move. Now `helprow` calls the list's own `updateAllItems` once after it swaps the rows, both ways (TRAINER in, or Inventory back when In-game menus goes off), so the row reads right on the glue's first frame. This is the data-and-refresh way of the brief's three: no hook, no node written directly. The glue still goes in two pause updates in at the earliest (section 12.5: `lm_ready`, then qwark's request), during the pause's opening animation (the list's `buttonBG3` fading in), so the row's first frames may still be the game's; nothing earlier can run in the pause's VM. Every safety property is as it was: the redraw is the list's own method, under `call`'s pcall, inside the push, and it changes nothing the take-over records.

## 16. Planets opens the galactic map (revision 1.29, pending)

The four original games' Trainers open their game's own planet picker from the root's Planets row (rewrite/docs/REPORT-planet-pickers.md, PROTOCOL.md 9.1 "The game's own planet picker"). Tools of Destruction's now does too: its picker is the ship's galactic map. This was the last feature-parity item of ToD's in-game Trainer. Read from the executable (Ghidra, DL-ghidra:/NPEA00452.ELF), the map's presentation (`built/anark/galacticmap/built.dat` in `global_cached.psarc`, its chunk `gmapHndler` decompiled with the session scratchpad's `nm/luapseudo.py`) and the levels' scripts; nothing here has run on a console yet.

### 16.1 How the game opens the map (high)

- **It is a game state of its own, 6**, not an overlay of the pause and not a screen of it: `GalMap_request` (0x35084) fills a state request (`GameState_queueOverlay`, op 2, state 6, enter `GalMapState_enter` 0x36598, exit `GalMapState_exit` 0x35B0C), which replaces gameplay (state 4) on the stack as the pause's own request does (op 2 calls the old state's exit and the new one's enter, `GameState_ApplyPending` 0x4C476C). Its two bytes go into the map's state (`g_galMap`, 0x101CBF84): +0x40 `loadOnPick` and +0x41 `canExit`.
- **Its callers are two**, and nothing else queues state 6 (every caller of `GameState_queueOverlay` and every writer of `g_gameStatePendingOp` read): the gameplay package's **`gmap()`** (`Lua_gmap` 0x291CBC: `GalMap_request(1, 1)`, through the thunk 0x26B7F0; tolua's wrapper 0x2B1B64, registered by `tolua_gameplay_open`), and the end of a space combat level (0x38EDB4, the space combat controller's update: `GalMap_request(1, 0)` once the level's next planet has been visited, a map you cannot leave without a pick). Of the levels' scripts only Fastoon's `aphelion.lua` calls `gmap()` itself (after the ship's repair: the unlocks, `gmap()`, then a fade in); the ship's own prompt (`PromptSpaceShip`, class 0x3E9, `hero_ship_flyout`) plays its departure cinematic (`l00_s001_rcin_rt`), and the map follows through `gmap()` (medium: the cinematic's own script, in level data, was not read; no other path to state 6 exists).
- **What it needs.** A level: `GalMapState_enter` builds the map's `AnarkMenuSystem` (0x14B0 bytes from the Anark arena, `GalMap_loadMenu` 0x36448; `g_galMapSystem` 0x101CBF80) and its 3D galaxy from the level's own map objects: every level's instances have `gmap_data` (the clue of class 0x43B that `GalMap_levelInit` 0x35C14 finds at the level's start, `g_galMap.data` +0x34) and the planets' mobys (`gmap_kerwan` .. `gmap_skydome`), all nineteen levels, the space combat ones included. Nothing else: not the ship, nor a part of the level. The pause cannot be up (both are states of the one stack, and both build an `AnarkMenuSystem` in the same arena), so the map opens from play.
- **The frame.** `GalMapState_update` (0x360BC, `g_gameState` 6's case of `GameState_Dispatch`) runs the map's `AnarkMenuSystem_update` and draws; no gameplay frame runs, so neither the gameplay VM nor the pause test does.
- **How it returns.** `exit_galactic_map()` (Back in its list mode, `GalMap_close` 0x35120) and a pick both go back to play through `GameState_requestGameplay` (with `canExit` set, or a level picked); `GalMapState_exit` frees the map, puts the level's view back (`GalMap_restoreView` 0x35920) and, with a level picked and `loadOnPick` set, calls `LoadLevel(level, force, 0)`, force for a space combat level.

### 16.2 The map's list and what it allows (high)

`gmapHndler` builds its rows in `initPlanetData`: a header per visible sector (`is_sector_visible`), then each level of `levelArray` in that sector that `is_level_visible` passes; `levelArray` is Cobalia, Stratus City, Fastoon, Fastoon II, the three space combat levels and every other level to Meridian City: **Metropolis (Kerwan) is not in it**. A row the cursor may pick is `is_level_visitable`. Select on a row zooms to the planet (`set_level_view`, slide 3), Select again calls `load_level(level)`; Back zooms out, and in the list closes the map.

- `is_level_visible`, `is_level_visitable` and `is_sector_visible` (one visitable level in the sector) all come down to **`GalMap_isLevelVisitable`** (0x36888): the level's `ToDLevelSave` (0x1020C2F8 + level x 0x408) `unlocked` byte (+0x400) set, the byte after `visited` (+0x402) clear, the level not 0, and Fastoon (3) only while Fastoon II (18) is not visitable. So the map shows what the save has unlocked, and one Fastoon, whichever the story is at.
- **A pick** is `GalMap_LoadLevel` (0x3705C): visitable again, then `GalMap_selectLevel` (0x351D8), which maps Mukow (5), Rykan V (9) and Kerchu City (14) to the space combat level before each (4, 8, 13) while that level's `visited` byte (+0x401) is clear, unlocking it, maps Fastoon and Fastoon II to whichever is unlocked, and stores the level in `g_galMap.selectedLevel` (+0x3C, 0x101CBFC0, -1 from `GalMapState_enter`) unless it is the level the player is on (outside a space combat level), then closes the map. The current planet picked is a close with no load.

### 16.3 The design

- **The Planets row** is the same link it was (no MBOX_CAP_PICKER, no MROWF_PICKER: those are for a renderer that opens its picker over the menu, and the map cannot be up with the pause). Its cross, where the map can open (struct menu_native's `picker`, ToD's `tod_galmap` in `tod_game.c`; a level's lua_State and the Lua helper in, `lua_core_gameplay_ready`), is a CLOSES action (menu.c `DEFER_PICKER`): the glue closes the pause as for a load (section 13), and once the game plays the core opens the map. Where it cannot, the Planets page opens as before, and the console says so ("Trainer: the galactic map cannot open here; the planets instead").
- **Opening it** (menu.c `native_picker_*`): the core writes the picker's pokes, each byte's own value read first, then sends **`gmap()`** to the gameplay VM, a request of its own of target 0 (`lua_core_gameplay_send`, as the glue goes to the pause's VM; never a LUA_EXEC's, logged if it fails). The game opens the map exactly as Fastoon's script does. No code is patched and nothing is hooked: the Lua helper, its glue and LUA_PATCH are unchanged, and it works under RPCS3 with the helper's patch as on a console.
- **Every planet the map can show** (the pokes, `tod_galmap_pokes`): while it is up, levels 1 to 17 `unlocked` 1 and +0x402 0, and the three space combat levels `visited` 1. So the map lists every level of its `levelArray` (all three sectors, every planet), each can be picked, and a pick loads the level picked (Mukow, Rykan V and Kerchu City no longer go to their space combat levels first). Fastoon II keeps the save's own byte, so the map's one Fastoon row is whichever Fastoon the save is at, as the game shows it. Metropolis is not in the map at all. The core keeps the table's addresses and values with the bytes (`g_gm`), so it can put them back even if the game's module goes.
- **Back**: `g_gameState` leaves 6 with `selectedLevel` -1. The core puts back every poked byte that still holds what it wrote (a byte the game changed meanwhile is the game's), and asks the menu to open again with an open request, as the combo does in play (the pause test takes it, the glue opens the Trainer), on its root with the cursor on Planets. That row then reads **ALL PLANETS**, and its cross opens the Planets page, the list of every planet (Kerwan and both Fastoons among them); after that, or once the Trainer leaves its root or closes, it is PLANETS and opens the map again. The open is asked for until the Trainer is up, for four seconds.
- **A pick**: `g_gameState` leaves 6 with a level in `selectedLevel`; the bytes go back the same way, the Trainer stays down, and the game's own load is under way: `GalMapState_exit`'s `LoadLevel` put the level into `g_planetLoadRequest`, so `LoadLevel_ProcessPending` fades (the game's 0.5 s, not qwark's one-frame fade of section 13) and the load screen plays. Fast loads cut it as any load, and the autosplitter sees it as any load (it watches the tier loader, not who asked). The bytes are back before the level loads (the fade alone takes half a second, and qwark looks thirty times a second).
- **A map that never comes** (the game's `gmap()` failing, or `g_gameState` not 6 four seconds after it was sent): the bytes back, "Trainer: the galactic map did not open; the planets instead" on the console, and the Trainer asked to open again on the Planets page.
- **Safety, unchanged**: nothing of the pause's VM changes (the pool guard, the push and pop gate, the take-overs and their restore, nothing wrapped while the Trainer is down: none of it is touched, the glue being the same bytes); the map's own presentation is the game's, untouched. The only writes are the 37 bytes of the save's level records, scoped to the map qwark opened, never to the game's own (the ship's) map, and put back at the first look after it has gone, on a failure, and when the session or the game's module goes (`menu_detach`, `menu_forget`).
- **Sizes**: the glue 7,949 bytes and LUA_PATCH 1,990 rows as before (no change); `tod.sprx` gains the picker's table (about 120 bytes); the core (`qwark.sprx`, test builds only) the driver and 384 bytes of state.
